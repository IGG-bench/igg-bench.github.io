Abstract

GUI grounding benchmarks ask whether an agent can localize a target that is already visible in a static screenshot. Real interfaces often violate this assumption: a target may be off-screen, appear only after a state change or hover, remain occluded, or become actionable after a delay. This leaves the ability to recover target visibility unevaluated. To measure this reveal step, we introduce Interactive GUI Grounding (IGG), a benchmark in which an agent must first make the target visible through interaction and then click it. IGG contains 601 tasks across 16 controllable GUI environments and seven visibility-constraint sub-types, with a compact action space of scrolling, moving, dragging, waiting, and clicking. In our human study, participants achieve 94.6% accuracy, while GPT-5.5 reaches 79.4% and the strongest evaluated open-source VLM reaches only 31.6%. To identify the source of this gap, we conduct two controlled interventions. Telling Qwen3-VL which interaction to perform raises its accuracy only from 30.8% to 33.9%, whereas performing the interaction for the model raises it to 81.9%. The bottleneck is executing the reveal interaction, not recognizing the target once it is exposed. We further show that this capability is learnable, demonstrating that visibility recovery can be strengthened consistently across model families.

Task examples

In every IGG task the target is not visible or not actionable in the first screenshot. The instruction names only the target, never the procedure, so the agent has to work out which interaction exposes it. An episode succeeds on the first click whose element ID matches the target.

The benchmark

IGG has 601 tasks across 16 controllable GUI environments modeled on familiar applications. Each environment starts from a deterministic state and gives every element a stable ID, so every click can be checked against the target at click time.

Tasks fall into seven sub-types under three constraint types:

  • CT1 Viewport: scroll-based exploration
  • CT2 Multi-State: visual disambiguation, hidden state activation, removable occlusion
  • CT3 Temporal / Manipulation: delayed state activation, dynamic target interaction, movable occlusion

The agent sees only screenshots, the instruction, and its own action history. The DOM, accessibility tree, and ground-truth trajectory stay hidden. It acts with five actions:

SCROLL(dir, Δpx)reveal off-screen regions
MOVE(x, y)trigger hover states or disambiguating cues
DRAG(x₁, y₁, x₂, y₂)move an element out of the way
WAIT(Δt)let delayed or asynchronous UI settle
CLICK(x, y)grounding is evaluated here

Where does it fail?

We split an episode into four stages: selecting a reveal action, executing it with the right location or parameters, recognizing the target, and localizing the final click. We then intervene at two of them. Telling the model which interaction is needed barely helps. Performing the interaction for the model recovers most of the gap.

So most errors happen in choosing where and how to perform the reveal, before target recognition is even tested. Target-agnostic heuristics show the same split: fixed scrolling, hovering, and waiting reveal 68.8%, 61.4%, and 87.1% of their matched tasks, while popup dismissal and occluder dragging reach only 17.6% and 16.9%.

Visibility recovery is learnable

Base VLMs never emit DRAG on the held-out tasks, so RL alone has nothing to reinforce. We first run frequency-balanced SFT on human-verified trajectories to bring rare reveal actions into the policy's support, then apply online GRPO with browser-executed rewards. On the 120-task held-out split this raises Qwen3-VL from 40.0% to 59.2% GA, and the same recipe gives similar gains on two other architectures.
